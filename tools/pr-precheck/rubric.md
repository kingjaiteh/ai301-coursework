# Rubric: is this pull request ready to submit?

Each check reads the artifact itself (the diff, the commands and their output, the repo's stated asks) against the plan, the issue and the repo facts. No check grades length, tone or formatting. Locations named in the Evidence column are mapped in `references/evidence-guide.md`.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | Every file and hunk in the candidate PR's diff, read against the plan's Files list, scope (in and not-in), approach and any deviation note in the plan context. | Every changed file and every functional hunk falls inside the plan's stated scope or a deviation note, AND every change the plan promises appears in the diff or is explicitly deferred in a deviation note. A shortfall the plan or its deviation note discloses passes. An unplanned functional change (a new option, flag, setting, refactor or rewrite of a file the plan never names) or a promised change missing with no note fails. | required |
| description-fidelity | Each factual claim in the PR title and description about what the change does, which files it touches, or what it leaves alone, read against the diff. | Every such claim is true of the diff: nothing the description says was changed is missing from the diff, and nothing it says was left alone (for example "no changes beyond the plan", "no functional changes elsewhere") is contradicted by the diff. A deferral the description states openly passes. A confident claim of fidelity over a diff that does more or less fails. | required |
| decisive-evidence | The test evidence section (and test results quoted in the description), read against the plan's test plan and the reproduction it built on, plus the repo-facts block's stated test command, if any. | For every failure mode the plan's test plan names, the evidence names the command or steps that re-run it and states the observed result after the fix, with the before result shown or cited from the repro; the re-run exercises the changed path, not a control or an unrelated path. Where the repo facts or template name a test suite or check command, the evidence names that command and its outcome. "Tested locally", "works now" or "tests pass" with no command named does not count. | required |
| clean-diff | The unified diff's added and removed lines, hunk by hunk. | The diff contains no debris: no debug prints or logging added for debugging, no commented-out code, no dead or unused functions, no TODO markers added, and no formatting, import-order or whitespace churn on lines the change does not need. Commit messages are not graded here. Unplanned functional changes are graded by plan-fidelity, not here. | required |
| template-followed | The repo-facts block's pull-request line (template sections, checklist, required links and entries) and contribution guide asks, read against the PR title, description and diff. | Every ask the repo states as part of a PR is met with real content: each named template section is present with substantive content (by content, not heading format), a required issue link ("Closes #N", "fixes #N") is present, a required checklist is addressed, and a required file entry (changelog, whatsnew) appears in the diff. Asks the repo marks optional ("if applicable", "if appropriate") cannot fail this check. If the repo states no template and no PR asks, it passes. | required |
| ai-disclosure | The repo-facts block's contribution policy (any stated AI policy), read against the PR description. Treat every package as AI-assisted work. | If the repo's stated policy requires disclosing AI use, the description contains a disclosure meeting what the policy asks (for example, the tool used and the extent of assistance). If the policy requires human-written text, the disclosure states the human wrote or reviewed it. If the repo states no AI policy, it passes. | required |
| thread-engaged | The thread highlights' explicit maintainer questions, asks or warnings, read against the plan context and the PR description. | Every explicit maintainer question or ask in the thread that bears on the change is addressed in the plan or the description, or no such ask exists. | preferred |

## Verdict rule

Accept (ready to submit) if every required check passes; otherwise reject (hold). Preferred checks are reported but never change the verdict. An `unclear` grade counts as a fail on every check: a claim that can't be verified from the package is a failing one.
